## A. 自回归解码机制（one token at a time）

- 核心：自回归模型一次生成一个 token，每个都条件于已生成的全部 token。
- 联合概率链式分解：`P(x_1,…,x_n) = ∏_{t=1}^{n} P(x_t | x_1,…,x_{t-1})`。
- 每步推理循环：① 用当前序列做一次前向传播 → ② 得到词表上的 logits → ③ softmax 得概率分布 → ④ 采样/argmax 选出新 token → ⑤ 追加回输入 → 重复，直到 EOS / 达到 max_length / 命中停止条件。
- 为何慢：每步都要完整跑一遍全部参数；token t 必须等 t-1 完成（严格串行依赖）；精确搜索全序列是 O(|V|^N)，不可行（50000 词表 × 20 token = 50000²⁰）。
- 因果掩码（causal/masked self-attention）：只能注意到过去 token，保证自回归。训练时用 teacher forcing 一次前向对所有位置算 next-token loss；推理时每生成一个 token 一次前向。
- KV Cache 是主要缓解：缓存历史 K、V，每步只算新 token 的注意力，把每步从 O(n) 重算降到 O(1) 增量。

来源：baampark.github.io（LLM Decoding）、cameronrwolfe.substack.com、arXiv:2412.19442（KV Cache 管理综述）、arXiv:2402.02057（Lookahead Decoding）。

## B. 温度（temperature）数学与边界条件（多源一致）

**公式（所有来源一致）：** `P(token_i) = exp(logit_i / T) / Σ_j exp(logit_j / T)`，即 `softmax(logits / T)`。
等价代数恒等式：`exp(logit_i / T) = (exp(logit_i))^(1/T)`——这解释了为何小 T 会「指数级放大」大 logit。

**边界条件：**
- T → 0：分布坍缩为 delta 函数（point mass）于 argmax，等价贪心解码。
- T = 1：标准 softmax（训练分布）。
- T → ∞：分布趋于均匀（最大熵），但**不是**所有 token 等概率（仍取决于原始 logits 相对大小）。

**熵关系：** T 直接控制采样分布的熵——低 T → 低熵 → 尖峰 → 确定；高 T → 高熵 → 平坦 → 多样。

**经验发现（arXiv:2506.07295《Hot or Cold?》，2025）：** 温度与性能总体负相关；机器翻译最优温度近 0（0+ε）；创造力任务中大/中模型最优约 T=1.3；指令遵循在 0–1 稳定，>1 出现「突变」；无放之四海皆准的最优温度。

来源：machinelearningmastery.com、medium（@harshit158 / @kyrylldekanenko）、arXiv:2506.07295、arXiv:2510.02611、Lilian Weng（Controllable Neural Text Generation）。

## C. 温度的常见误解（对抗核验过）

- **「温度=创造力参数」——证伪。** Peeperkorn et al.（arXiv:2405.00492, ICCC'24）：温度与新颖性弱相关、与不连贯中等相关，与连贯/典型性无关；「温度-创造力」远比传说复杂且弱。
- **「0–1 调温显著影响解题准确率」——证伪。** Renze & Guven（arXiv:2402.05201）：0.0–1.0 区间温度对解题**无统计显著影响**（GPT-3.5，1000 道选择题，五种 prompt 条件 p 值全 >0.05）；文本相似度随温度下降（说明参数生效），但准确率不变——温度改的是表层多样性，不是推理质量。
- **「温度=0 完全确定」——语境依赖。** 温度=0 只让**采样这一步**确定（argmax）；生产环境因 **batch 不变性**（不同 batch 组成改变浮点归约顺序）、浮点不可结合性、MoE 路由等仍可能不可复现。OpenAI/Anthropic/GCP 文档均承认「即使 T=0 也不完全确定」。但在**隔离的本地硬件、无优化**下，T=0 可复现（arXiv:2408.04667 实测 Llama3-8b 本地确定）。根因是生产基础设施（batching、硬件异构），非温度本身。
- **「对 greedy/beam 调温度有用」——证伪。** 温度改分布形状但**不改 token 排名**；greedy/beam 按排名选，故温度对它们无效。

来源：arXiv:2405.00492、arXiv:2402.05201、arXiv:2506.07295、arXiv:2408.04667、sebastianraschka.com、mikulskibartosz.name、martynassubonis.substack.com、zansara.dev。

## D. greedy / beam search / top-k / top-p 对比

- **Greedy**：`w_t = argmax P(w | w_{1:t-1})`，等价 T=0。缺陷：易重复、陷入局部最优、「路径盲」；长文本生成质量差（HuggingFace 官方）。
- **Beam Search**：每步保留 num_beams 个最可能假设，最后选整体概率最高。「总能找到比 greedy 概率更高的序列，但不保证最可能」。缺陷：开放式生成中**重复、单调**（neural text degeneration）；「beam search 诅咒」——beam 越大质量反而下降。擅长机器翻译/摘要。违反「均匀信息密度（UID）」假说（人类倾向信息均匀分布）。
- **Top-k**：只保留概率最高的 k 个，归一化后采样。缺陷：k 固定，不适应分布尖/平。（Fan et al. 2018 引入，k=10。）
- **Top-p / Nucleus**：保留累积概率刚超过 p 的最小集合（动态核），截断「不可靠尾部」。（Holtzman et al. 2019，见 L 节。）
- **关键结论**：解码策略效果**任务特定**，无普适最优（Wiher, Meister, Cotterell, arXiv:2203.15721）。

来源：HuggingFace《How to generate text》、AssemblyAI、arXiv:2203.15721、Lilian Weng、arXiv:1904.09751、arXiv:1811.02549。

## E. 重复惩罚与 HuggingFace GenerationConfig（精确）

**Repetition Penalty（CTRL 论文 arXiv:1909.05858 引入，HF 实现）：**
HF 源码公式：`score = where(score < 0, score * penalty, score / penalty)`。penalty > 1 时，正负 logit 都被推向更小/更负，降低已出现 token 概率。penalty=1 无变化；<1 反而鼓励重复。作用于 **prompt + 已生成文本**。CTRL 作者建议 ~1.2。

**三种惩罚区别（vLLM 文档）：**
- `repetition_penalty`（CTRL 式，乘除型）：覆盖 prompt+生成；二值（是否出现）。
- `presence_penalty`（OpenAI 式，加减型）：仅生成文本；二值。`logit_i - α·I(i∈g)`。
- `frequency_penalty`（OpenAI 式，按频次）：仅生成文本；按出现次数缩放。`logit_i - β·count(i,g)`。
注：`presence_penalty` / `frequency_penalty` 不在 HF GenerationConfig 原生参数里（是 OpenAI API 参数）。

**HF GenerationConfig 关键默认值：** `max_length=20`、`do_sample=False`、`num_beams=1`、`temperature=1.0`、`top_k=50`、`top_p=1.0`（<1 才激活核采样）、`repetition_penalty=1.0`、`no_repeat_ngram_size=0`、`length_penalty=1.0`、`num_assistant_tokens=20`（投机解码）。

来源：arXiv:1909.05858、github.com/huggingface/transformers（logits_process.py）、HF GenerationConfig 文档、vLLM SamplingParams 文档。

## F. KV Cache（精确显存、中文源、MLA/量化）

- 复杂度：无 KV Cache 时注意力 O(n²)；有 KV Cache 后每步增量，整体近 O(n)。中文社区共识：「以空间换时间」。
- 单 token KV：`2 × n_layer × n_head × d_head × dtype_size`（2=K,V）。整 context：再乘 context_length × batch。
- 精确数字（多源对抗确认）：
  - Llama-2-7B（FP16）≈ 0.5 MB/token；128K context = 64 GB（> 14GB 权重）。
  - Llama-2-13B ≈ 0.78–0.8 MB/token；4K×batch8 ≈ 25 GB。
  - 实测示例：开 KV Cache 后某段生成 42s → 9s（约 5×）。
  - LLaMA-2 7B / A100 40GB：无缓存每后续 token 10ms；有缓存 2ms（100 token 提速 ~71%）。
- **GQA / MQA**：Llama-2-70B 用 GQA（64 query heads / 8 KV heads = 8× 缩减）。Mistral-7B 4× 缩减。
- **DeepSeek MLA（多头潜注意力）**：低秩 KV 联合压缩，KV Cache 降 **93.3%**，生成吞吐 5.76×（DeepSeek-V2 官方论文 arXiv:2405.04434，多源确认）。
- **量化**：FP8/INT8 降 50%，INT4 降 75%；KIVI（2-bit）2.6× 峰值显存降、<2% 精度损失。
- 缓存淘汰/压缩（综述 arXiv:2603.20397）：H2O、SnapKV（8.2× 显存效率、3.6× 生成提速、单 80GB GPU 跑 Qwen-7B 380K context）、MorphKV、RocketKV（400× 压缩）等。

中文高质量源（知乎正文 403，标题/热度供参考）：「图解 KV Cache」「KV Cache 量化技术详解」；可访问镜像：博客园 LexLuc（4407 阅读）、53AI（19196 阅读）、百度云（325333 阅读，含 LLaMA-2 7B A100 基准）、vizuara.substack（MLA 解析）。

来源：arXiv:2603.20397、arXiv:2405.04434、introl.com、omrimallis.com、rohan-paul.com、知乎/博客园/百度云镜像。

## G. vLLM / PagedAttention 详解（精确）

- 论文：Kwon et al.（UC Berkeley Sky Computing Lab），SOSP 2023，arXiv:2309.06180，DOI 10.1145/3600006.3613165。
- 核心问题：传统系统按最大长度预留连续 KV 内存，**浪费 60–80%**（预留 + 内部碎片 + 外部碎片）；有效利用率仅 20–40%。
- PagedAttention：KV Cache 切成固定大小 block（默认 **16 token**），block table 映射逻辑位置→物理地址，非连续按需分配；「受操作系统经典虚拟内存与分页启发」。**浪费降至 <4%**；利用率 40%→96%+。
- 性能：吞吐 **2–4× vs FasterTransformer/Orca**；vs HuggingFace Transformers **最高 24×**（单完成 14–24×，三并行 8.5–15×）；vs HF TGI 最高 3.5×。并行采样/beam search 内存共享降 **55%**，吞吐 +2.2×。
- 单 token KV（OPT-13B）：`2 × 5120 × 40 × 2 字节 = 819,200 字节 ≈ 800KB`；2048 token ≈ 1.6GB。
- GitHub：vllm-project/vllm（调研时 84.3k star，2836 贡献者，900+ 贡献者另一说）；2023-06-20 首发；2025-05 入 PyTorch Foundation。LMSYS Chatbot Arena 生产用，GPU 减半，日均 3 万请求峰值 6 万。

来源：vLLM 官方博客（2023-06-20）、arXiv:2309.06180、RunPod、阿里云开发者社区（Se7en258）、百度开发者中心、Red Hat、Continuum Labs、知乎镜像。

## H. 连续批处理 / 投机解码 / 吞吐-延迟权衡

**Continuous Batching（Orca, OSDI 2022）：** iteration-level scheduling（按单步而非整请求调度）；selective batching（非注意力算子批处理，注意力单独处理）。吞吐 **36.9× vs FasterTransformer**（GPT-3 175B）。AnyScale 实测：连续批处理 8× vs naive，+ PagedAttention 23× vs naive（OPT-13B，A100 40GB）。静态批处理常仅 ~35% GPU 利用率。

**Speculative Decoding（投机解码）：**
- Leviathan et al.（ICML 2023, arXiv:2211.17192）+ Chen et al.（DeepMind, arXiv:2302.01318），2022–2023 并行提出。
- 机制：小 draft model 生成 γ 个候选，大 target model 一次并行验证；rejection sampling **可证保持原分布（无损）**。
- 加速：通用 2–3×（60–80% 接受率）；EAGLE 2.5–2.8×；草稿模型一般为 target 的 1/10–1/50。
- **陷阱**：大 batch（≥32）下退化——arXiv:2310.18813：batch=32 时投机长度应 ≤2；batch=128 时比自回归多耗 25.65% 能量。decode 在大 batch 下变 compute-bound，draft 开销无法摊销。vLLM 实测：高 QPS 下 1.4–1.8× 性能下降。
- 适合：代码生成、结构化输出（JSON/SQL）、模板化、可预测任务；不适合：创意写作、高并发离线批处理。

**吞吐-延迟权衡（Sarathi-Serve, OSDI 2024, arXiv:2403.02310）：** 「no free lunch——同一硬件无法同时最小化延迟、最大化吞吐」；prefill/decode 混批产生 prefill stall；chunked prefill、P/D 分离（Splitwise、Mooncake）是解法。

来源：friendli.ai/research/orca、anyscale.com、arXiv:2310.18813、arXiv:2403.02310、bentoml.com、redhat developer、vLLM 官方博客。

## I. SSE 流式（「打字机效果」的工程来源）

- 机制：模型逐 token 生成；服务端用 **SSE（Server-Sent Events）** 每生成一个 token 即推送，`Content-Type: text/event-stream`，`data: {...}\n\n`，结束 `data: [DONE]`（OpenAI）；Anthropic 事件序列 `message_start → content_block_start → content_block_delta → content_block_stop → message_delta → message_stop`。
- SSE vs WebSocket：SSE 单向（服务器→客户端）、基于 HTTP、浏览器自动重连、CDN 友好；WebSocket 双向、需握手。仅当客户端也要实时回传才用 WebSocket。
- 关键指标：**TTFT（首 token 时延）** 决定何时看到第一个字；**TPOT（每 token 时延）**。「首 token 一两秒内出现，即使全文 10–15 秒」。
- 体验：用户感知流式比缓冲快「约 40%」（单源、无引用，谨慎用）；进度感让人愿等「约 3 倍」时长（Nielsen Norman 引用）。
- 坑：反向代理（Nginx）缓冲会让流式静默退化为批式——需 `X-Accel-Buffering: no`；HTTP/1.1 每域 6 连接限制，HTTP/2 多路复用解决。

来源：Simon Willison（til.simonwillison.net）、OpenAI/Anthropic 官方流式文档、redis.io 博客、tpiros.dev、Anthropic Python SDK（DeepWiki）。

## L. 核采样（Nucleus / Top-p）溯源（合并 6 支子调研，对抗核验）

**原始论文：** Holtzman, Buys, Du, Forbes, Choi，《The Curious Case of Neural Text Degeneration》，arXiv:1904.09751（2019-04-22 首次提交），ICLR 2020。（华盛顿大学 + AI2；Yejin Choi 团队。）

**摘要核心三结论：** ① 最大化解码（greedy/beam）不适合开放式生成；② 当前 LM 概率分布有「不可靠尾部」需截断；③ 核采样是当时最佳的长文本解码策略（质量高且多样性接近人类）。

**定义：** top-p 词表 `V^(p)` = 使累积概率 `Σ_{x∈V^(p)} P(x) ≥ p` 的**最小**集合；再在其上重归一化采样。动态：模型自信时核小（几个 token），不确定时核大（上百 token）。

**Table 1 关键数字（ar5iv 两次核验确认）：** 重复率——greedy 73.66%、beam(16) 28.94%、纯采样 0.22%、top-k(40) 0.78%、**nucleus(0.95) 0.36%**、人类 0.28%。困惑度：nucleus 13.13 vs 人类 12.38。HUSE：nucleus 0.97。推荐 p ∈ [0.9, 1)。

**术语溯源：** 论文自己叫 **"nucleus sampling"**；"top-p" 作为算法名是社区命名——最早见 openai/gpt-2 PR #133（2019-05-16，nshepperd，"Implement nucleus (top-p) sampling"），经 Thomas Wolf/HuggingFace gist（`top_p` 参数）+ OpenAI GPT-3 API（2020-06，`top_p` 官方参数）固化。论文正文用 "top-p vocabulary" 作为 `V^(p)` 的标签。

**先验技术核查（结论：无）：** 2019-04 前无任何论文/系统用「累积概率阈值动态截断词表」。最接近的前身是 Fan et al. 2018（top-k，固定 k=10，ACL 2018，arXiv:1805.04833）——核采样是其「动态 k」推广。温度采样（Ackley 1985 起）只重塑分布不截断。Diverse beam search（2016）、stochastic beam search（Shao 2017 / Kool 2019）均按 rank 而非概率质量。OpenAI GPT-2 首发（2019-02）不含 top_p，2019-08-27 才加（"nucleus sampling" commit）——晚于 Holtzman 4 个月，确认是采纳自该论文。

来源：arXiv:1904.09751、OpenReview（ICLR 2020）、ar5iv、aclanthology P18-1082（Fan et al.）、openai/gpt-2 PR #133、thomwolf gist、Wikipedia「Top-p sampling」、arXiv:2009.07243 / 2210.15191（采样综述）。
